Under the Hood

Two systems do most of the runtime's work: a multithreaded event loop that powers async/await, and the reference-counting allocator that manages every heap value. This page walks through both with architecture diagrams, then compares marina's approach with Swift, Go and Rust.

The event loop & async threads

Marina compiles async functions ahead of time into state machines — there is no VM, no interpreter, and no green-thread scheduler. The compiled binary links libmarina_runtime.a, which starts a small thread pool and a timer thread. Every blocking operation (fs, net, sql, http) runs as a task on the pool; continuations after await are tasks too.

  • Worker pool — min(hardware_concurrency, 8) threads pulling from a shared task deque under one mutex + condition variable.
  • Timer thread — a binary min-heap of setTimeout entries ordered by (due, seq); a due timer becomes an ordinary task.
  • Quiescence — the main thread blocks in marina_event_loop_run() until no queued tasks, no running tasks, no pending timers, no unresolved promises, and no listening HTTP servers remain, then the process exits.

What await actually does

The compiler splits every async function at each await into segments. Each segment is a case in a generated resume(frame, state, value) function — the frame is a plain heap block holding the locals. await promise compiles to marina_await(promise, resume, frame, next_state): the frame is parked and the worker thread moves on immediately. When the promise resolves, a waiter task runs the continuation on some worker thread — the value crosses threads by reference-counted ownership, never by shared mutable state.

async function load(path: String): String {
    let text = await fs.readFile(path)   // parks the frame here
    return crypto.sha256(text)          // runs in a continuation segment
}

The same machinery backs setTimeout (timer → task) and promise executors (new Promise runs synchronously, JS semantics). Promises are ARC-managed too: creating one registers it as pending so the loop can't exit while work is outstanding.

The HTTP accept loop

Blocking servers (http.listen) occupy one listener thread, but the express-style server.listen(host, port) uses a poll(2)-multiplexed accept loop — a single thread watches every connection's file descriptor, so thousands of idle keep-alive connections cost nothing until they have data. Handlers are async: each request becomes a task on the worker pool.

Memory management: ARC

Every heap value — strings, arrays, objects, promises — carries a 16-byte header with a lock-free atomic reference count. The compiler inserts retain/release calls during codegen: a value assigned into a variable, array slot or object field takes a +1; overwriting or leaving scope drops it. When a count hits zero the object is freed immediately and deterministically — there is no garbage collector, no tracing, no pauses.

A few rules make this safe across threads: counts are atomic (a value can be retained on one worker and released on another), element drops are deep (freeing an array releases every element), and background tasks record an Owns list of retained payloads that is released when the task finishes — so an I/O task can't outlive its arguments.

Swift — ARC with escape hatches

Swift is marina's closest cousin: the compiler also inserts retain/release. Swift additionally has weak/unowned references and autorelease pools; marina currently has neither (cycles leak, same as a Swift cycle you forgot to break).

class Node {
    var next: Node?          // strong reference
}
var a = Node()
var b = Node()
a.next = b
b.next = a        // cycle: both stay at rc = 1 forever → leak

class Parent {
    weak var child: Child?   // weak: does not bump the refcount
}

Go — the runtime decides

In Go you never think about ownership: objects live as long as they are reachable, and the concurrent collector (tri-color mark & sweep with write barriers) reclaims them — cycles included — in background cycles with very short stop-the-world phases. The price is a bigger heap and CPU time you don't control.

type Node struct {
    next *Node
}

func main() {
    a := &Node{}
    b := &Node{}
    a.next = b
    b.next = a
    a, b = nil, nil   // cycle is unreachable — the GC collects it
    runtime.GC()      // ...at some point like this (or on its own)
}

Rust — the borrow checker decides

Rust enforces a single owner per value at compile time. Assignment moves; borrows (&/&mut) are checked so no aliasing mutation can exist. Nothing runs at runtime — which is why there are no refcount atomics and no GC pauses — but shared mutation needs explicit opt-in (Rc, RefCell, Arc, Mutex).

struct Node {
    next: Option<Box<Node>>,   // Box: single owner, freed on drop
}

let a = Node { next: None };
let b = a;              // move — `a` is no longer usable
// println!("{}", a.next.is_none()); // compile error: value moved
let r = &b;             // borrow — checked at compile time

use std::rc::Rc;
let shared = Rc::new(Node { next: None });  // opt-in refcounting
let also = Rc::clone(&shared);              // rc: 2

Marina — ARC in an AOT C++ runtime

Marina programs read like Swift: plain assignment, no annotations, deterministic destruction. The counting happens in the generated LLVM IR calling the C runtime — marina_retain / marina_release — so it behaves exactly like the diagram above: freeing is immediate, cycles leak, and there is no collector to tune.

class Node {
    public name: String
}

let a = new Node()       // rc = 1 (a owns it)
let b = a               // same object — retain (+1)
b.name = "shared"

let list = ["a", "b"]   // array owns its element strings
let copy = list         // retain the array (+1), elements untouched

// when a, b, list, copy leave scope the compiler emits:
//   call void @marina_release(ptr %b)
//   ...
//   call void @marina_release(ptr %list) ; frees when the count hits 0
// (a reference cycle would keep both counts above 0 — same as Swift)
Design rule of thumb: Swift's ergonomics + Rust's determinism, without Rust's type-system burden. The trade-off accepted for v0.2 is that reference cycles leak — same as Swift with strong references — while Go would have collected them.
